# agenda-whatsapp-mvp

PWA for a single business to manage appointments; end customers book and get reminders only through WhatsApp (Cloud API).
Designed to become a multi-business product later (`business_id` everywhere), but only one business is built now.

## Specs

- S1. Product shape: "solo el negocio , el cliente solo va a utilizar whatsapp, por ahra un solo negocio la idea es ahcer un producto general". The business uses the PWA; customers use only WhatsApp. Data model carries `business_id` from day one.
- S2. Delivery as PWA, not native app: "la idea es tener un pwd, ya que no quiero hacer aplicacion para celular para no desplegar en play store o apple store".
- S3. Stack: "react, hono, postgrasql, docker para contenerizar todo ,drizzel orm, better auth, react hook form, tanstack query, shadcn/ui tailwind, zustand". Plus Zod ("si metamos zod"), pg-boss for reminders ("3 vale probamos"), React Router (user selected "React Router (recomendado)").
- S4. Purpose: "una app que envie recordaoriso whatsapp y me ayude a agendar citas", about "100 persoans al mes".
- S5. Stage 1 (base): pnpm monorepo (`apps/web`, `apps/api`, `packages/db`, `packages/shared`), Docker Compose with Postgres + api + web, Hono and React responding, Drizzle with its first migration.
- S6. Stage 2 (login): Better Auth with one business user.
- S7. Stage 3 (data model): business, services, opening hours, appointments, with a DB constraint that prevents overlapping bookings.
- S8. Stage 4 (agenda PWA): day and week views; create, move, cancel appointments; installable PWA.
- S9. Stage 5 (WhatsApp): idempotent webhook and menu-based bot (lists/buttons) to book, view, cancel.
- S10. Stage 6 (reminders): pg-boss worker sending `utility` templates on confirmation and 24 h before.

- L28 (coordinator, T6 design): scope is reminders only (no human handoff, payments, marketing). (1) pg-boss runs a worker inside the API process on the same Postgres (own `pgboss` schema); the dependency is added to `apps/api` only. (2) Source of truth is the new table `appointment_reminders` (migration 0005, generated then hand-checked, no `drizzle-kit push`): `id`, `business_id`, `appointment_id` (composite FK so it cannot cross businesses), `kind` (`confirmation`|`reminder_24h`), `due_at`, `status` (`pending`|`sending`|`sent`|`failed`|`skipped`), `attempts`, `sent_at`, `whatsapp_message_id`, `last_error` (no credentials or phone numbers), `created_at`, UNIQUE (appointment_id, kind); the business-removal helpers learn the table. (3) Any appointment creation (PWA API and WhatsApp bot, through the shared data-layer function) inserts in the same transaction a `confirmation` due now and a `reminder_24h` due at starts_at - 24h (omitted when already past); cancel -> pending reminders `skipped`; move -> only the 24h reminder is re-timed (skipped if past), the new time is not re-confirmed in this stage; a cancelled or past appointment is never reminded. (4) A pg-boss schedule `reminders-sweep` runs every minute: it claims due `pending` rows with FOR UPDATE SKIP LOCKED, moving them to `sending` with a lease (a `sending` row older than 5 min is retaken), re-checks at send time that the appointment is still `booked`, in the future and the customer has a phone, resolves the channel through `whatsapp_channels` (none -> `skipped` with `last_error`), sends, then marks `sent` with the message id; transient errors (network, 5xx, 408, 429, same classification as the webhook) return to `pending` with backoff 1/5/30 min up to 4 attempts, then `failed`; other 4xx -> `failed` at once. Sending is claimed in the database before the Graph call, so a row is never sent twice, except that a crash after the Graph call may repeat once after the lease (documented). (5) `WhatsAppClient.sendTemplate` (Graph `type: template`, name, language, body text parameters); env `WHATSAPP_TEMPLATE_CONFIRMATION`, `WHATSAPP_TEMPLATE_REMINDER`, `WHATSAPP_TEMPLATE_LANGUAGE` (default `es`), empty in compose; body parameters in order: customer name (fallback `cliente`), service name, date `dd/mm/yyyy`, time `HH:mm`, in the business timezone. Reminders are on only with WhatsApp enabled AND both template names set; exactly one set -> the API refuses to start; disabled -> nothing is scheduled or sent and appointments work as before. The `utility` category is a Meta-side template setting, documented in the README. (6) Injectable clock; the sweep is an exported function tested directly; pg-boss start/stop in `server.ts` with graceful shutdown, not started when reminders are disabled nor in unit tests that do not need it. (7) The README documents reminders, env vars, templates, retries, the crash-repeat limit and that real delivery was not verified against Meta.
